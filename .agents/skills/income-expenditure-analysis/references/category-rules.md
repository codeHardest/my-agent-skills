# 分类规则全集

规则全部来自真实账本逐笔复核过的经验。**关键词按顺序匹配，命中即返回**——顺序即优先级，不能乱。

**覆盖优先级（从高到低）**：
1. `TRANSACTION_OVERRIDES`（交易级，按 来源+日期+金额 精确指定）——支付宝导出脱敏、同一商户横跨多类别时用（如美团订单只见 `it_***@meituan.com`，但外卖餐饮与按摩/买药都是「美团」）
2. `CATEGORY_OVERRIDES`（商户级，按 交易对方+商品说明 关键词）——支付宝自带分类标错时用（地铁站「优鲜购」被标家居家装、收钱码小吃摊被标商业服务/酒店旅游、**金 被标教育培训）；**先于**支付宝自带交易分类与微信关键词。真实账本示例：扫码点单→餐饮美食、皇婴汇→母婴亲子、聚充充/竹芒→生活服务（充电宝租借）、课时→教育培训（志跃体育 4,122 压过运动户外「志跃」）
3. `TRANSFER_CATEGORIZE`（转账仍可归类的商户关键词）——微信转账/群收款默认往来，命中住房/房租关键词按消费归类（「贝壳廖敏玲」= 付房东房租）
4. 支付宝自带交易分类 → 微信关键词 → 个人往来判定

三条覆盖表都维护在 `scripts/analyze_expenses.py` 顶部，**新商户/新纠错先加覆盖表再跑**。

**微信「当前状态」列**：`已全额退款` 的行**整笔排除、不再计入**（支出侧与退款侧都不出现），不依赖退款单号配对——全额退款的退款行商户单号多为空，靠 (来源,单号) 配对会落空（真实账本：龙石战争/南方医院 共 109.00）。

**输出展示**：分类汇总表/Excel/图表/明细章节中「其他」**固定排最后一项**（无论金额大小）。

**个人往来判定**（规则全未命中后才走）：
- 交易类型 ∈ {转账, 群收款} → 转账往来；但命中 `TRANSFER_CATEGORIZE`（贝壳/租房/物业/房东/公寓/房屋/房租）按消费归类——「贝壳廖敏玲」= 贝壳平台付房东房租 → 住房物业；**群收款 ≤ 100 元** → **其他**（拼单/团体收款视为消费，如 刘伟 68.45、Linna 50.00）
- 交易类型 ∈ {扫二维码付款, 二维码收款} 且金额 ≤ 100 元、关键词未命中 → **其他**（小额扫码视为消费，用户规则）；>100 元仍走下列个人判定
- 交易类型 ∈ {商户消费} 且金额 ≤ 100 元、关键词未命中、且非可识别往来（微信转账到QQ/商品含「转账」）→ **其他**（如 余红昌 4.00、小岳 10.00、Lz 10.00×3）
- 对方名以 `商户_` 开头 → 金额 ≤ 100 元 → **其他**；>100 元 → 转账往来
- **转账往来兜底判定（非整百 → 其他）**：所有落入转账往来的判定点（转账/群收款/个人扫码 >100/商户_ >100/支付宝收钱码）最后统一过 `transfer_or_other(金额)`——金额**非整百 → 其他**（真实转账多为整百金额，非整百的多是消费误标为转账，如 杰瑞鼠 20、李美凤 109、无本万利 265、支付宝 *巧 169）；整百 → 转账往来。银行流水转家人不受此规则影响（真实整百大额）。
- 去掉 emoji 后精确命中名单，或名单内 ≥2 字昵称作为子串出现，或匹配 `^[一-龥]{2,3}$` / `中文名(` → 转账往来（仍先过非整百判定）
- 名单需按真实流水持续扩充（转家人、亲密昵称等）

## 银行：分流顺序（先剔除 → 储蓄 → 直付消费 → 往来/内部）

对银行流水每条支出，**按下列顺序**第一个命中的生效：

```
1. 信用卡还款 → 剔除重复结算（对应支付宝信用购等消费）
2. 蚂蚁 | 基金 | 20884215521324210156(支付宝基金户) | 大额存单 | 银证 | 证券 → 储蓄投资
3. 财付通 → 剔除重复结算（对应微信流水消费）
4. 支付宝 → 剔除重复结算（对应支付宝流水消费）
5. 京东 | 网银在线 | 拼多多 | 淘宝 | 抖音 → 网购/平台（直付，计入）
6. 广州久伴 | 房屋租赁 → 住房物业（直付，计入）
7. ATM | 支取现金 → 现金（直付，计入）
8. 岭南通 → 交通出行（直付，计入）
9. 充值 → 充值缴费（直付，计入）
10. 本人账户号 → 内部转账
11. 转账 | 转账汇款 → 转账往来
12. 快捷支付 或 无法判定 → 其他（直付，计入，逐笔复核）
```

> 第 2 步必须压住第 4、5 步：储蓄对方名可以带结算/购物字样（如「大额存单开户…支付宝（中国）网络技术」——本是大额存单却会被支付宝误判；蚂蚁基金户里的「京东」也不会误入网购）。第 6 步的房租账户号（如招商 1109613270100010508399419）要在个人名之前判断，避免家人转账被误判为房租。招行的个人转账还须核对收款卡号（base64：`NjIyMTgwNTU1MDAwMDU3NTQ0Ng==`）。

## 主力购物平台拆解（单列 sheet）

拼多多/淘宝/京东/抖音 上的**全部消费**（含全品类，不限「网购/平台」类别）单独拆一个 sheet/章节——用户关心的是「在哪买的」，一个平台的商品可能落在日用百货/服饰/餐饮等多个类别，都归到该平台下。按「交易对方/银行明细」匹配，命中即归属：

```
拼多多: 拼多多 拼好货
淘宝:   淘宝 天猫 淘特
京东:   京东 网银在线    # 网银在线是京东支付网关
抖音:   抖音
```

- 匹配不到的购物类商户归「其他平台」，不进拆解表（如需更多平台，按「扩充新商户」补关键词）
- 同一平台在不同来源的消费（微信/支付宝/银行直付）都归到该平台下

## 退款冲减（退款不体现在账单里）

退款不在账单/明细里单列展示，而是**冲减到原交易**：

1. 以（来源, 商家/商户单号）把退款配对到原消费行——多数导出里退款与原交易的单号相同
2. 全部退款的交易 → 整行移除（该笔不再出现在明细，类别净额=0）
3. 部分退款的交易 → 明细按净额显示单行，备注注明「退款冲减 X」
4. 配对不上单号的退款 → 按同类别支出行吸收冲减；仍有余额则计入复核要点
5. 复核要点给出退款合计（如「退款冲减共 30.00 元」），保证可追溯

## 加班打车报销（不计入消费）

网约车支出里属于「加班打车」的部分由单位报销，**不计入个人消费**。报销金额体现在银行流水收入中：

1. **报销收入 R**（两条识别路径，满足其一）：
   - 含「报销」且与出行相关（打车/滴滴/网约车/加班/差旅/交通）→ 记入 R
   - 命中**已知报销入账方**（`REIMBURSE_PAYEES` 的账号/名称，如 8110901013501308779 / 广州腾讯凯博信息）→ 记入 R，但**排除**：代发工资行（那是工资）、金额 ≥ 工资额度上限（`REIMBURSE_SALARY_FLOOR`，报销多为小额）的大额入账——被排除的入账方行写进复核要点请用户核对是否为工资/奖金
   - 真实账本里报销入账行文不含「报销」二字（雇主以「转账…」入账加班打车报销），**只能靠对方识别**，识别不了的报销路径靠用户补充
2. **网约车支出 T**：交易对方/明细含 滴滴/网约车/曹操/T3/享道，**并排除零售商户**（`RIDE_NEG_KW`：便利店/超市/商店/零售/百货）——「东网约车便利店」是便利店不是网约车，真实账本 2025-07-09 8.00 曾因此被误判
3. **剔除额 = min(R, T)**：从交通出行中剔除，单列「加班打车(已报销)」sheet/章节，不计入消费
4. 报销金额对账：R > T 或 R < T 都写进复核要点（如「网约车支出 25 元中已报销 15 元，剩余 10 元仍计入交通出行」），金额不完全对齐时请用户核对订单；报告中列出计入 R 的每笔收入行，供对账

## 如何扩充新商户

新增一个陌生商户时，先判断它是「能映射到既有类别」还是「新类别」。若是前者，把该商户的关键词加进对应类别的关键词列表（放列表尾部，规则按顺序不影响旧结果）；若是后者，先问用户归入哪类，再补规则。**每加一条规则，重跑一次并确认总金额不变**（除非你本就想改变某笔的归类）。

新增主力购物平台同理：在 `PLATFORM_KEYWORDS` 尾部加一行（如 唯品会/苏宁），并确认该平台消费已被对应类别规则命中。新增报销类型（如 差旅/餐补报销）时：在报销识别里补对应关键词，并确认其对应的支出类别（如 酒店旅游/餐饮美食）按同规则剔除。
