In this lesson, you will learn what code review is, how it fits into the developer workflow, and the differences between human and AI code review. You'll explore the goals of effective code review, correctness, maintainability, knowledge sharing, and risk reduction and understand how AI code review systems work under the hood. So let's dive in.

So, what is code review? In software development, code review is when a proposed code change is examined thoroughly before it becomes part of the main code base. Imagine you're a developer building a new feature in a project management app. And that feature is about adding a priority field to a form. When you make a PR, the code that changed includes the UI form being updated and a database schema change. On the surface, everything looks fine. This code change, however, is a bit riskier than it looks because older parts of the app have not taken this priority field into account. So this could easily be a breaking change that a code review process could have caught. Someone could point out that with every database schema change, you should run a migration or a backfill process and add graceful degradation with conditional logic so that the application doesn't break. And that's essentially what we do in code review.

What's not always included in code review? The focus of code review is typically code quality, structure, readability, standards and adherence. These are source code changes in incremental phases before merge, which is different than quality assurance. Quality assurance is about product behavior and use from the end-user with more of a business perspective. It's about entire features, workflows, integrations and getting ready for cutting a new release.

Let's break down exactly where code review happens in a developer workflow. The developer typically receives a coding task from a project management tool, like Jira or Linear, like building a new feature or reducing technical debt. Then they begin implementing the task locally. This happens in their coding environment on their machine, could be an IDE, code editor, terminal, or coding agent workspace. Once they've made meaningful progress, this code is committed on a new branch off of the main code base and submitted into a version control system like GitHub as a pull request or merge request. This brings visibility to the code and allows for other developers on a team to review the changes carefully. If they identify issues, they can request changes. Once the code is considered to be in good condition, team members can approve the code and the developer who originally wrote it can safely merge it into the main codebase.

Now let's look at the code review problem heat map in the age of Gen AI. When humans are writing code and humans are reviewing it, this is a typical state of software engineering that we've had for decades. There have always been some successes and some challenges or friction with this. But now that AI code review is introduced, this helps human-written code be analyzed at a much faster rate, which alleviates some of the arduous work involved in code reviews in the first place. However, with AI-generated code, this creates a massive bottleneck for manual human reviews. We're talking thousands of lines per PR and hundreds of PRs a week. This leads to Comprehension debt. When a developer begins losing the ability to understand what's going on in the code base due to the large amounts of AI generated code. This can lead to another major potential risk, rubber stamping. Due to the rate at which developers feel pressured to push code through the pipeline, this leads to almost blindly approving pull requests and merging them into the main code base. What we find is much more manageable is when the speed of AI generated code is met with the quality and speed of AI code review tools. In this case, developers could still blindly trust all AI output too easily, but AI code review can help maintain a certain level of code quality, which alleviates some of the pressures of moving fast without breaking things.

Let's look at the difference between human review and AI Review. For human reviews, we have a very nuanced subject matter expertise as one of the main strengths. especially within the constraints of an engineering team and the whole company that they work for. A team of engineers are more likely to know what's best for the code and how to change it safely, ultimately giving them the final judgment power, despite any AI tools that they may use to develop and review code. One of the major limitations is that for every hour that a developer spends reviewing code, there are only about 400 lines of code that will receive high quality attention before a decline in the ability to effectively review it. For AI review, some of the strengths are its ability to synthesize its analysis of code changes and present them by level of importance and severity. These automated code review processes can run from anywhere between a couple of minutes and seven minutes, which is ideal for many sizes of code changes or even up to thousands of lines of code in a PR. One of the limitations is that to maximize the power of AI code review, it requires a context integration of your developer tooling and workflows. Think Jira for planning, coding agent sessions, architectural docs, coding rules, etc.

Now, how do they work together? The strengths are that AI can be a first pass and then a human can step in with their subject matter expertise and be the final judgment step with business context. AI can summarize the changes in code review, and then a human can dynamically apply attention to the most important callouts that it summarizes. Therefore, you can apply your attention to what matters most instead of treating every single PR or every single line of code equally. Because they're subjective in value depending on what you're building and the nature of the code change.

Whether or not you're using AI to conduct code reviews, there are some overarching goals to make them very effective. Correctness, does this code do what it should? Maintainability, can the developer understand and safely change it? Shared knowledge. Can developers learn from information shared during code review? and risk reduction. While code can be correct, that doesn't mean that it's not introducing some new security risks. Uncovering risk and addressing it before merging the code is incredibly valuable in the code review process.

In a previous example, we covered a hidden issue with adding a priority field to a database and UI form. A strong code review catches this issue and identifies the need for a backfill, for default handling and null safe logic, so that the feature works correctly for both new and existing data by updating the PR to address this, it improved code correctness at the code review stage.

For maintainability, think of a scenario where you have an app.tsx file that includes UI rendering, Form state, API calls, Validation, Table logic, and Error handling. That's 500 plus lines of code where that one file is doing everything. and a small change can easily break unrelated code. This calls for an opportunity to refactor where you break down different aspects of the code into different components and hooks and utilities and API files. Each file has one job. Changes are a lot easier to isolate and easier to understand, and therefore much easier for the next developer to read and maintain it safely.

For sharing knowledge in traditional code review, it's always been about whether developers can learn from the code review comments. Imagine a new developer who's onboarding onto your team and creating a new PR for a user dashboard, and it contains both UI and fetch logic. A senior developer then comes into the PR and adds a comment, We usually put server calls in hooks so components can stay focused on UI. Now that that comment's been made, the new developer has learned something about the way you shape your code and can adopt that shared pattern. Because of this conversational teaching moment, the new developer improves the code and this teaches other devs how to structure similar code the very next time they work on a similar task in that repo.

One thing that's important to mention is how sharing knowledge has evolved in the age of Gen AI using code review. A user can ask AI a question and an AI system can generate an answer. With agents using models and specialized tool calling, they can educate developers on code changes like a chat interface. For example, when a code review agent identified a shell command injection security bug in a PR. I asked, what are the risks of this shell command injection in a real user scenario? The agent's answer was a very detailed description of multiple risks if this code were to slip through into production. Now, I have the evidence to back up why this issue is critical. And I can take that with me into how I write safer code in the future. Or I can update our coding agent's skills and markdown files to address it in our AI coding workflow.

Risk reduction in code review processes is very important. Here's an example. Let's say you write a piece of SQL code where a search term is directly injected into a query. The code technically works, but it carries some risk. Developers and/or AI review tools can flag that this code exposes the app to injection attacks and it's also teaching a bad security pattern. Therefore, a parameterized query is an approved pattern because it's much safer. And with a proper fix, you have implemented a new piece of code without introducing risk from potential bad actors or users to your software.

Now, while AI is extremely helpful with the code review process, it can also create issues if the quality of the system is low. Let's imagine an AI code review tool analyzes a Pull request and presents findings to improve the code. Here are the different potential issues. Noisy comments. If your PR is suddenly getting flooded with dozens or more comments, and some of these comments seem to be nitpicks as opposed to very important callouts. This could be an indication of low precision. Or what happens if the tool misses some real issues that you could have caught or uncovered yourself? Now we would call that low recall. If it can't provide proper evidence, such as pointing directly to lines of code or relevant markdown files, we would consider that weak evidence. And that can make a developer question the accuracy of its suggestions in the first place. In the case that your coding standards evolve, if the system can't detect that and provide the up-to-date references to its context, we would call that a context gap. In all of these cases, this directly impacts the developer's ability to confidently review the code and rely on the system as a whole. This goes to show how important it is for an AI code review system to be high quality and help augment developers' work.

Here's how the system or these agents work under the hood. When a developer opens a PR, one or more AI agents will be triggered to run against the code change. They retrieve context from a knowledge base and analyze the change against that context to generate candidate findings. The system then synthesizes, ranks, and filters findings, so developers are presented with code issues, an explanation of the code change, and suggested fixes.
