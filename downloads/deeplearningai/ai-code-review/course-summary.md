## 课程概述

本课程由 DeepLearning.AI 与 Qodo 合作开设，教授如何在软件开发工作流中使用 AI 代码审查（Code Review）智能体，并从零开始构建自己的代码审查智能体，从而深入理解这些系统的工作原理——以便更好地使用它们。

### 课程结构

课程包含 8 个核心视频，按以下顺序学习：

1. **Introduction** — 课程介绍
2. **Overview of AI Code Review** — AI 代码审查概述
3. **AI Code Review Best Practices – Part 1** — AI 代码审查最佳实践（上）
4. **AI Code Review Best Practices – Part 2** — AI 代码审查最佳实践（下）
5. **Why Context Matters** — 为什么上下文至关重要
6. **Building a Context Engine** — 构建上下文引擎
7. **Building Specialized Code Review Agents** — 构建专门的代码审查智能体
8. **Conclusion** — 课程总结

### 课程主要学习目标

- 理解高效代码审查的核心目标，以及 AI 代码审查与传统人工审查的区别
- 学习实用技术，使 AI 审查者产出更好的结果（如本地预 PR 审查、提供丰富的任务和仓库上下文、基于潜在影响优先级排序发现的问题）
- 理解为什么上下文通常是审查质量的最大因素，以及为什么仅使用更强大的模型如果没有正确信息是不够的
- 从零开始构建上下文感知的 AI 代码审查系统
- 学习构建上下文引擎来检索相关代码
- 通过组合具有不同专业领域的专门智能体来扩展审查者

## 视频 2: Overview of AI Code Review（AI 代码审查概述）

**时长**: ~12 分钟 (724 秒)  
**链接**: https://learn.deeplearning.ai/courses/ai-code-review/lesson/de16nq/overview-of-ai-code-review  
**视频 ID**: 10172857

### 内容总结

本节课将学习什么是代码审查、它如何融入开发者工作流，以及人工代码审查与 AI 代码审查之间的区别。还将探讨有效代码审查的目标——正确性（Correctness）、可维护性（Maintainability）、知识共享（Shared Knowledge）和风险降低（Risk Reduction），并理解 AI 代码审查系统在底层是如何工作的。

**核心要点**:

1. **什么是代码审查**
   - 在软件开发中，代码审查是在提议的代码变更成为主代码库的一部分之前对其进行彻底检查
   - 例子：在项目管理应用中添加优先级字段到表单的 PR，表面看起来不错，但实际上存在风险（老代码未考虑此字段，可能造成破坏性变更）
   - 代码审查应该指出：每次数据库 schema 变更时，都应运行迁移或回填过程，并添加条件逻辑的优雅降级
   - 代码审查**不包括**：通常不关注产品质量保证（QA），QA 关注的是从最终用户角度的产品行为和使用

2. **开发者工作流中代码审查发生的位置**
   - 开发者通常从项目管理工具（如 Jira 或 Linear）接收编码任务
   - 然后在本地实施任务（IDE、代码编辑器、终端或编码智能体工作空间）
   - 一旦取得有意义的进展，代码被提交到新的分支上，提交到版本控制系统（如 GitHub）作为 PR
   - 这使代码可见，并允许团队中的其他开发者仔细审查变更
   - 一旦代码被认为处于良好状态，团队成员可以批准代码

3. **AI 时代的代码审查问题热力图**
   - 当人类编写代码且人类审查代码时，这是软件工程的典型状态，已有几十年历史
   - 现在引入了 AI 代码审查，帮助更快地分析人工编写的代码
   - **AI 生成代码带来的问题**：
     - 人工审查出现大规模瓶颈（每周数千行代码和数百个 PR）
     - **理解债务（Comprehension debt）**：开发者开始失去理解代码库的能力
     - **橡皮图章式批准（Rubber stamping）**：开发者感到压力，几乎盲目地批准 PR 并合并到主代码库

4. **人工审查 vs AI 审查的对比**
   
   **人工审查的优势**：
   - 非常细致的主题专业知识（在工程团队和整个公司的约束内）
   - 工程师更可能知道什么对代码最有利，如何安全地更改代码
   - 拥有最终判断权
   
   **人工审查的局限**：
   - 每小时开发者审查的代码量有限（约 400 行代码后审查能力下降）
   
   **AI 审查的优势**：
   - 能够综合分析代码变更并按重要性和严重性级别呈现
   - 自动化代码审查可在几分钟到七分钟内运行，适合任何规模的代码变更
   - 甚至可以处理 PR 中多达数千行代码
   
   **AI 审查的局限**：
   - 需要开发者工具和工作流的上下文集成（Jira 规划、编码智能体会话、架构文档、编码规则等）

5. **人工 + AI 如何协同工作**
   - 优势：AI 可以是第一关，然后人类可以凭借其主题专业知识和业务上下文进入最终判断步骤
   - AI 可以总结代码审查中的变更，然后人类可以动态地将注意力应用于最重要的提示
   - 因此，可以将注意力集中在最重要的事情上，而不是平等对待每个 PR 或每行代码

6. **有效代码审查的总体目标**
   - **正确性（Correctness）**：这段代码做了它应该做的事吗？
   - **可维护性（Maintainability）**：开发者能否理解并安全地更改它？
   - **共享知识（Shared Knowledge）**：开发者能否从代码审查过程中共享的信息中学习？
   - **风险降低（Risk Reduction）**：虽然代码可能是正确的，但并不意味着它没有引入一些新的安全风险

7. **每个目标的实例说明**
   - **正确性实例**：添加优先级字段到数据库和 UI 表单，代码审查应识别需要回填、默认处理和空安全逻辑
   - **可维护性实例**：500+ 行的 app.tsx 文件包含 UI 渲染、表单状态、API 调用、验证、表格逻辑和错误处理，应该重构为不同的组件、hooks、工具和 API 文件，每个文件只有一个职责
   - **共享知识实例**：新开发者创建包含 UI 和 fetch 逻辑的 PR，资深开发者评论"我们通常将服务器调用放在 hooks 中"，通过这种对话式教学时刻，新开发者改进了代码
   - **AI 时代的共享知识演进**：用户可以向 AI 提问，AI 系统可以生成答案。智能体使用模型和专门的工具调用，可以像聊天界面一样教育开发者
   - **风险降低实例**：SQL 代码中搜索词直接注入查询，代码技术上工作，但存在 SQL 注入攻击风险，应使用参数化查询

8. **低质量 AI 代码审查系统的问题**
   - **嘈杂的评论（Noisy comments）**：低精度的表现
   - **遗漏真实问题（Low recall）**：错过了你本可以自己捕获的真实问题
   - **弱证据（Weak evidence）**：无法提供适当的证据（如直接指向代码行或相关 markdown 文件）
   - **上下文差距（Context gap）**：无法检测编码标准的演变并提供最新的上下文引用

9. **AI 代码审查系统在底层的工作原理**
   - 当开发者打开 PR 时，一个或多个 AI 智能体将被触发对代码变更运行
   - 它们从知识库检索上下文，并针对该上下文分析变更以生成候选发现
   - 然后系统合成、排序和过滤发现，因此开发者会看到代码问题、代码变更的解释和建议的修复

**核心知识点**:
- 代码审查的四个核心目标：正确性、可维护性、知识共享、风险降低
- AI 时代的问题：审查瓶颈、理解债务、橡皮图章式批准
- 人工 vs AI 审查的优劣势对比
- 人工 + AI 协同工作模式
- 低质量 AI 审查系统的常见问题：嘈杂评论、低召回、弱证据、上下文差距
- AI 审查系统的底层工作流程

## 视频 3: AI Code Review Best Practices – Part 1（AI 代码审查最佳实践 - 上）

**时长**: ~9 分钟 (556 秒)  
**链接**: https://learn.deeplearning.ai/courses/ai-code-review/lesson/79yprh/ai-code-review-best-practices-%E2%80%93-part-1  
**视频 ID**: 10172858

### 内容总结

本节介绍 AI 代码审查的三个基本最佳实践：运行预 PR 审查以尽早发现问题，使用独立的代码审查智能体，并提供详尽的任务级上下文以帮助 AI 代码审查工具识别需求差距并验证实现。

**核心要点**:

1. **最佳实践 #1：始终使用独立的代码审查 harness**
   - **原因**：当我使用 Claude Code、Codex 或其他 AI 编码智能体时，它们是为代码生成而设计和优化的
   - 当 PR 由智能体生成时，我将其传递给独立的代码审查工具，该工具针对的是发现代码中的风险，而不是生成代码
   - 它们内置了对抗性智能体，涵盖高质量工程标准，并发现高优先级问题
   - 你无法仅依赖你的编码智能体可靠地发现这些问题

   **实例对比**：
   - 在支付应用的 PR 中添加支付状态模型的新字段
   - 让 Codex（编写代码的同一智能体）审查它 → 只标记出核心本地正确性问题（如果 payment 处于 under_review 状态，capture 端点仍可捕获它）
   - 使用单独的 harness 作为 AI 代码审查 → 结果更广泛，发现相同的 bug（Capture 绕过审查状态），还根据编码规则（如文档字符串要求）和下游服务的破坏性变更发现更多问题
   - **关键点**：一个有用的 AI 评论不应该是整个审查体验。需要独立分析，使用严格为代码审查优化的复杂 AI 系统

2. **最佳实践 #2：在 PR 提交前运行预 PR 审查**
   - **原因**：来自其他开发者的注意力是昂贵的，重要的是要谨慎对待这一点
   - 在提交 PR 之前进行 AI 和人工审查有助于捕获代码中较小规模的问题

   **实例对比**：
   - **没有预 PR 审查**：在 contracts 仓库添加新的支付处理状态 under_review，发现 9 个问题（2 个 bug、2 个需求差距、5 个跨仓库冲突）
   - **进行预 PR 审查**：在 Codex 中先要求它审查代码并应用本地修复，然后独立 AI 代码审查工具在 PR 阶段进行更广泛、更深入的整体代码审查
     - Codex 提出 5 个问题（4 个 P1、1 个 P2）
     - 同样的代码变更提交后，独立审查只发现 3 个问题
   - **关键点**：开发者可以将注意力集中在这些更高信号的发现上，因为之前的本地审查已处理了一些变更或修复

3. **最佳实践 #3：提供详尽的任务级上下文**
   - 如今，人类和 AI 智能体都在任务管理工具（如 Jira 或 Linear）中创建和管理工作
   - 无论是我自己还是我的智能体在写这些工单
   - **不要**：在工单中提供很少的需求或信息，因为很少的上下文意味着你的 AI 代码审查系统不会有足够的信息去对比代码变更
   - **应该**：提供非常清晰的问题解决方案详细信息，然后将其作为上下文引入到代码审查中
   - 让我的智能体写详尽的工单，给我的代码审查智能体提供衡量代码的标准，就像我自己审查代码一样

   **实例对比（任务 vs 审查结果）**：
   
   **工单 DX-4（模糊、不充分的需求）**：
   - 一句话的工单总结
   - 几个关于代码期望的注释
   - AI 代码审查结果：4 个问题（缺少文档字符串、缺少枚举、缺少 web 状态视图、硬编码状态枚举）
   
   **工单 DX-3（详尽的需求）**：
   - 具体标题："Prevent capture for payments under manual review"
   - 包含目的、用户故事、长长的验收标准列表
   
   **同样的代码变更在 PR #12 中**：
   - 同样的代码变更：添加状态到支付 API
   - 但使用了详细工单 DX-3 作为上下文
   - 结果：识别出**两个需求差距**，都被列为"action required"（应在合并到主分支之前处理）
   - 详细解释：PR 引入了 under_review 的支付状态，但端点无条件地将支付状态设置为 captured 并发出 capture 事件，这违反了阻止 under_review 支付事件并返回 409 冲突的要求
   - Jira 工单作为上下文证明代码差异违反了任务的需求
   - 列出的证据直接连接到 Jira 中的工单
   - 不仅可以看到代码中不充分的地方，还有连接到原始任务意图的证据

**核心知识点**:
- 三大最佳实践：独立代码审查 harness、预 PR 审查、详尽的任务级上下文
- 代码生成与代码审查应分离
- 开发者注意力是宝贵资源，应通过预 PR 审查减轻负担
- 工单（任务）的详细程度直接影响 AI 代码审查质量
- 需求差距的识别需要上下文支撑

## 视频 4: AI Code Review Best Practices – Part 2（AI 代码审查最佳实践 - 下）

**时长**: ~12 分钟 (732 秒)  
**链接**: https://learn.deeplearning.ai/courses/ai-code-review/lesson/jcm17p/ai-code-review-best-practices-%E2%80%93-part-2  
**视频 ID**: 10172859

### 内容总结

本节介绍如何通过提供仓库规则和组织标准作为上下文，并通过按风险严重性分类发现的问题以首先关注关键问题，从而最大化 AI 代码审查的有效性。还将发现如何将反馈转化为可重用的智能体技能和标准，并使用 AI 代码审查作为交互式对话来加深你对代码的理解并减少理解债务。

**核心要点**:

1. **最佳实践 #4：提供仓库和组织标准作为上下文**
   - 我坚信单个代码差异并不能真正解释你的软件需要如何构建
   - 例如，工程标准存在于 Confluence 中，这些标准可以在代码审查中用作上下文
   - 它直接链接到与需要审查的代码最相关的文档
   
   **实例说明**：
   - 在支付应用 API 仓库中，简化 capture 重试处理流程的 PR
   - 审查使用的上下文显示了审查的依据：Confluence 支付标准（10 条相关规则）、相关的智能体技能、两个相关仓库
   - 打开"Idempotency weakened for capture"问题：指向需要 Idempotency-Key 的具体规则 → 连接到 retry-safety 技能 → 解释为什么重复事件请求可能产生重复工作
   - **关键点**：强大的 AI 审查不应该只是猜测我的团队或我如何构建软件。我给它相同的规则、文档、智能体技能和任何其他系统上下文，帮助我对它实际发现的问题建立信心。然后我可以介入，成为负责任的人工审查者

2. **最佳实践 #5：按风险级别审查代码**
   - 我自己就是这样做的
   - 当我提交 PR 并且代码审查智能体开始分析代码时，会出现几种不同类型的问题发现，我需要能够解读如何处理每一个
   
   **风险级别分类**：
   - **低风险**：可安全地由智能体自动修复
   - **中等风险**：建议开发者注意，可能需要讨论权衡或确定是否是预期的变更
   - **高风险**：需要开发者注意，影响安全、数据完整性和系统行为
   
   **关键点**：AI 代码审查不应使每条评论都显得同等紧迫。它的工作是引导我的注意力，让我知道什么可以快速处理，什么需要开发者判断，什么应该实际阻止合并。

   **实例对比**：
   
   **PR #24 中的"Idempotency weakened for capture"（Action required）**：
   - 此变更删除了 Idempotency-Key 强制执行，使重试不安全
   - 在支付流程中，可能产生重复的 capture 事件和重复的结算工作
   - 有大量证据匹配 → 应阻止合并，需要代码修复和证明重放过程安全的测试
   
   **PR #24 中的"readme contract is out of date"（Review recommended）**：
   - 文档不匹配，但不会造成破坏性变更
   - 正确的行动取决于意图：可以更新此变更以配合代码中的其他变更，或将其作为单独的 PR
   - 较低风险、较低优先级

3. **进一步：通过 Q&A 挑战 AI**
   - 挑战 AI，进行 Q&A，或真正使其成为对话而不是自动接受它带来的每个问题
   
   **实例**：
   - 询问："shell command injection 在真实用户场景中的风险是什么？"
   - AI 代码审查提供的响应：远程代码执行（容器）、密钥/token 外泄、特权升级
   - 这些信息可以带到学习代码审查过程中，成为参与的开发者
   
   **PR #19 实例**：
   - 在支付应用 API 仓库的 PR #19 中，做了一个有 bug 的小变更（如缺少 idempotency-key 强制执行）
   - 询问："除了代码正确性之外，如果实际合并此问题还涉及哪些其他风险？"
   - 响应：API 契约合规性、运营、下游一致性风险（其他服务）、财务工作流的对账风险、整体可靠性和监控
   - **关键点**：你不只是盲目接受建议，你在互动并学习不同的代码问题。这是 Q&A 在审查中的最佳使用方式

4. **最佳实践 #6：创建新的规则和智能体技能（让代码库学习）**
   - 随着我的代码演进，使 AI 智能体更强大的上下文工程实际上需要与之一起演进
   - 越来越多的代码审查工具正在将**记忆层（memory layer）**集成到系统中
   - 这意味着我在代码审查中使用得越多，它就会更好地针对我偏好的代码方式进行微调

   **循环过程**：
   - **审查（Review）**：AI 呈现审查发现
   - **判断（Judge）**：我仍然做出判断 — 这是一次性问题、嘈杂的建议还是值得保留的真实模式
   - **捕获（Capture）**：如果我相信这是一个真实模式，则可以将其捕获为编码标准或智能体技能
   - **重用（Reuse）**：AI 代码审查系统的记忆层被更新，未来代码审查可以自动使用该上下文
   
   **实例**：
   - 在支付应用技能仓库中，使用 Codex 自动化迭代 AI 代码审查工具在 PR 中浮现的重复问题
   - 创建了一个新的 PR，添加了一个可在代码审查期间使用的技能，以改进代码的 capture-retry-safety 区域
   - 技能内容：帮助代码审查者知道标记任何削弱的 idempotency-key 验证、可能发生的任何类型的重复事件、不安全的状态转换以及任何潜在的契约漂移
   - 最重要的：它说"重复结算事件应该是代码审查工具浮现的 action required"
   - 一周后创建另一个 PR，"context used"中显示智能体技能 capture-retry-safety 被调用
   - 因为它被确定为与过去浮出的重复问题最相关
   - 这就是**代码库学习**的方式：**Review, Judge, Codify, Reuse** — AI 代码审查系统和流程应承认你的标准并将其推进到你未来做的工作

**核心知识点**:
- 三大补充最佳实践：仓库标准作为上下文、按风险级别审查、创建可重用智能体技能
- 记忆层（memory layer）让代码审查工具随时间进化
- Review → Judge → Capture → Reuse 的循环
- Q&A 模式：与 AI 对话而非被动接受建议
- AI 代码审查不应使每个评论都同等紧迫

## 视频 5: Why Context Matters（为什么上下文至关重要）

**时长**: ~6.5 分钟 (397 秒)  
**链接**: https://learn.deeplearning.ai/courses/ai-code-review/lesson/vtdr22/why-context-matters  
**视频 ID**: 10172855

### 内容总结

本节通过比较两种方法在许多合成 PR 上的表现，解释为什么上下文感知的代码审查明显优于仅差异（diff-only）审查。将看到如何为审查者提供代码库模式和任务需求使其能够捕获从差异本身看不见的模式违规。理解上下文质量可能比模型本身更重要。

**核心要点**:

1. **实验设置**
   - 在本实验中，首先仅使用代码差异审查 PR
   - 仅差异方法导致较低的精确率（precision）、召回率（recall）和 F1 分数
   - 然后通过为审查系统提供代码上下文和任务需求（除了差异之外）来增强审查
   - 通过额外的上下文，精确率、召回率和 F1 三项指标都有显著改善
   - 为了使比较有意义，将跨 15 个不同的 PR 重复此评估，汇总结果，并比较仅差异方法与上下文感知方法的总体性能

2. **单个 PR 的分析**
   - **PR 内容**：添加用户配置文件更新端点
   - **预期问题**：与身份验证、授权模式和 try-except 错误处理相关的问题（处理方式不佳）
   - **代码审查系统的提示**：包含代码审查提示、PR 标题、任务部分、代码差异、上下文部分和说明
   - 这些是可以传入参数的占位符，但模型将生成问题列表及其相应的严重性级别

3. **仅差异审查者（Diff-Only Reviewer）的结果**
   - 仅差异审查者发现了 4 个问题
   - 涉及身份验证、授权以及围绕错误处理和未处理异常的安全问题
   - 2 个高严重性、1 个中等、1 个低
   - 与预期的 2 个问题相比，**没有匹配**的发现

4. **上下文感知审查（Context-Aware Review）的结果**
   - 在这种情况下，使用更多上下文运行相同操作
   - 总共 3 个发现
   - **质量不同**：描述中引用了被违反的不同模式，更多关于授权和身份验证以及 try-except 块的错误处理
   - 与预期问题相比：**两个预期问题都匹配**了上下文感知审查发现的问题

5. **15 个 PR 的评估结果**
   - 在所有 15 个合成 PR 上评估两种方法
   - 评估指标：
     - **精确率（Precision）**：代码审查结果与已知结果的匹配程度
     - **召回率（Recall）**：实际捕获的已知问题集的比例
     - **F1 分数**：平衡两者
   
   **关键数据**：
   - **精确率**：17.5% 增加
   - **召回率**：43.3% 增加
   - **F1 分数**：25.4% 增加
   
   **结论**：代码审查系统的整体质量通过添加上下文显著增加

6. **每个 PR 的详细结果**
   - 在每个 PR 上，可以看到仅差异代码审查发现 0 到 2 个问题
   - 但对于为 PR 运行的每个上下文感知审查，**所有两个预期问题都被发现**
   - 从仅差异到上下文感知结果的一致改进

7. **关键洞察**
   - 在本课中，我们学到了将正确的上下文添加到代码审查系统的强大能力
   - 在下一课中，将深入构建上下文引擎，以控制为代码审查系统找到最相关的上下文

**核心知识点**:
- 上下文感知的代码审查明显优于仅差异审查
- 关键数据：精确率 +17.5%、召回率 +43.3%、F1 +25.4%
- 在 15 个 PR 上的一致改进
- 上下文质量比模型本身更重要
- 模式违规需要上下文才能被识别

## 视频 6: Building a Context Engine（构建上下文引擎）

**时长**: ~6 分钟 (366 秒)  
**链接**: https://learn.deeplearning.ai/courses/ai-code-review/lesson/53tjuk/building-a-context-engine  
**视频 ID**: 10172883

### 内容总结

本节学习如何从分块（chunking）到嵌入（embeddings）和向量搜索构建上下文检索系统，以为上下文感知的审查提供动力。将发现使用最相关的代码块的选择性上下文检索实际上胜过转储更大的代码上下文。

**核心要点**:

1. **实验设置**
   - 在上一个实验中学会了上下文如何重要
   - 在本实验中，专注于使用正确的上下文
   - 首先使用完整的代码库作为代码审查的上下文 → 导致较低的代码审查质量和较低的 F1 分数
   - 然后通过构建上下文检索引擎增强审查，使用它为每个 PR 从代码库中检索相关上下文，并使用更相关的上下文进行代码审查
   - 使用这种方法，代码审查质量有所改善
   - 跨 15 个 PR 重复评估，汇总结果并比较两种方法的总体性能

2. **构建上下文引擎的步骤**

   **步骤 1：加载 FastAPI 仓库**
   - 25 个仓库文件，总共 1126 行代码
   - 在真实世界中，这是相当小的仓库，但对于测试上下文引擎对代码审查系统最相关上下文的抓取是足够的
   
   **步骤 2：基于 AST 的分块（AST-based chunking）**
   - 用于从代码库中提取函数和类
   - 枚举内容并显示类型、名称和文件路径
   - 创建了 99 个块，分布在类、函数和一个测试之间
   
   **步骤 3：转换为向量嵌入（Vector Embeddings）**
   - 使用 OpenAI 的 **text-embedding-3-large**
   - 允许我们在关键字匹配之外找到语义相似的代码
   - 创建了 99 个嵌入，并显示了它们维度的样本
   
   **步骤 4：存储嵌入在 Chroma 中（向量数据库）**
   - 用于快速相似性搜索
   - 创建了包含 99 个块的向量索引
   
   **步骤 5：测试检索**
   - 在示例 PR 上测试检索并查看检索了哪些块
   - 查询："Add user search functionality"
   - 检索到的顶部块：list_users、search_reports 等函数

3. **上下文大小的对比**
   - **完整上下文（Full Context）**：99 个块，超过 31000 个字符
   - **选择性上下文（Selective Context）**：只有 15 个块，近 3500 个字符
   - **88.9% 的减少**
   - 在真实世界中，选择性上下文在 token 成本方面更高效，并且由于检索到的这种选择性上下文，可能会获得更精确的代码审查

4. **三种方法的评估结果**
   - 在所有 15 个 PR 上评估了三种方法：
     - 无上下文（No Context）
     - 完整上下文（Full Context）
     - 选择性上下文（Selective Context）
   
   **关键发现**：
   - 无上下文时精确率较低（符合预期）
   - 使用所有块和使用仅前 15 个最相关的块之间有上下文跳跃
   - 最终改进 F1 分数
   - **结论**：使用选择性上下文实际上优于完整上下文

5. **可视化对比**
   - 基于上下文的添加，但更重要的是基于聚焦检索的选择性上下文，它在所有指标上都优于拥有完整上下文和完全没有上下文

6. **上下文大小与审查质量的权衡**
   - 在比较选择性上下文和完整上下文的图表中：
     - 使用完整上下文时，质量下降，最终影响 F1 分数
     - Y 轴（更高更好）与 X 轴（更低更好）的对比

7. **关键洞察**
   - 在本课中，我们看到了当上下文非常选择性时，上下文质量比提供的上下文数量更重要
   - 在下一课中，将更深入地了解专门的智能体流程，这些流程最终也可以提高代码审查的精确率

**核心知识点**:
- 上下文检索系统构建流程：分块 → 嵌入 → 向量存储 → 相似性搜索
- AST-based chunking 用于提取函数和类
- text-embedding-3-large 用于语义相似性
- Chroma 向量数据库用于快速相似性搜索
- 选择性上下文比完整上下文表现更好（88.9% 减少但质量更高）
- 上下文质量 > 上下文数量

## 视频 7: Building Specialized Code Review Agents（构建专门的代码审查智能体）

**时长**: ~5 分钟 (300 秒)  
**链接**: https://learn.deeplearning.ai/courses/ai-code-review/lesson/jcm17m/building-specialized-code-review-agents  
**视频 ID**: 10172884

### 内容总结

本节学习如何将具有领域专业知识的专门智能体与单一通用目的审查者的性能进行比较，同时管理成本质量权衡。将使用上一课构建的相同上下文引擎，先进行安全代码审查，然后进行代码库模式代码审查。最后，集成代码审查智能体将合并两个发现以生成最终的代码审查结果。

**核心要点**:

1. **实验设置**
   - 在本实验中，使用上一课构建的相同上下文引擎：
     - 先进行安全代码审查
     - 然后进行代码库模式代码审查
     - 最后，集成代码审查智能体将合并两个发现以生成最终的代码审查结果
   - 这可以导致更高的代码审查质量
   - 跨 15 个 PR 重复评估，汇总结果，并比较使用专门智能体的总体性能与通用代码审查的结果

2. **构建过程**
   - 在之前的课程中，使用了上下文，构建了上下文引擎，然后利用选择性检索改进了代码审查系统的整体指标和质量
   - 现在，看看专门的智能体如何协同工作以胜过我们构建的过去的代码审查系统

3. **集成架构（Ensemble Architecture）**
   - **安全智能体（Security Agent）**：检测漏洞
   - **模式合规智能体（Pattern Compliance Agent）**：查找代码库模式
   - **集成（Ensemble）**：合并两个发现并去重
   - 两个智能体将并行运行，将对结果进行去重并得出最终的代码审查结果

4. **专门智能体的特点**
   - 专门智能体倾向于有更长、更领域特定的提示
   - **提示字符数对比**：
     - 通用智能体：411 字符
     - 安全智能体：2300 字符
     - 模式智能体：~1700 字符

5. **评估结果**
   - 跨所有 15 个 PR 比较通用代码审查与利用所有专门智能体的集成
   - **重要**：两种方法的上下文引擎保持不变，只是智能体发生了变化

   **关键结果**：
   - 对于集成架构：
     - **精确率增加**
     - **召回率略有下降**
     - **总体 F1 分数增加**
   - **结论**：使用专门智能体时，最终胜过通用智能体架构
   - 在真实世界中使用代码审查系统时，高得多的精确率可以减少从实际代码审查中获得的结果中的噪声
   - 较少的噪声导致开发者能够随着时间推移信任实际结果

6. **视觉对比**
   - **集成架构：71.1% F1**
   - **通用智能体：60.6% F1**
   - 改进现在很明显，来自使用的安全和模式合规智能体

7. **每个 PR 的详细性能**
   - 每个 PR 都有预期的问题数量，以及捕获的匹配预期问题与捕获的总数之间的性能差异
   - **集成架构在多数情况下都明显胜出**

8. **关键洞察**
   - 在本课中，看到了具有领域专业知识智能体的专门集成架构实际上如何改进代码审查的整体质量
   - 还可以记住，使用前几课中的相同上下文引擎的一致性，对于维护和改进代码审查系统的质量也至关重要
   - 但加入集成架构可以获得更好的结果

**核心知识点**:
- 集成架构（Ensemble Architecture）：安全智能体 + 模式合规智能体 + 集成
- 专门智能体的提示更长、更领域特定（2300 vs 411 字符）
- 集成架构在 F1 上优于通用智能体（71.1% vs 60.6%）
- 高精确率 → 更少噪声 → 开发者更信任
- 上下文引擎 + 专门智能体 = 最佳组合

## 关键概念总结

### 核心概念

- **代码审查的四个目标**：正确性（Correctness）、可维护性（Maintainability）、共享知识（Shared Knowledge）、风险降低（Risk Reduction）
- **AI 时代的新挑战**：审查瓶颈、理解债务（Comprehension debt）、橡皮图章式批准（Rubber stamping）
- **上下文感知的代码审查**：明显优于仅差异审查（精确率 +17.5%、召回率 +43.3%、F1 +25.4%）
- **上下文检索引擎**：基于 AST 的分块 → 向量嵌入 → Chroma 向量数据库 → 相似性搜索
- **选择性上下文 vs 完整上下文**：选择性上下文（仅前 15 个块）在 F1 上优于完整上下文（99 个块），且减少 88.9% 的字符
- **集成架构（Ensemble Architecture）**：安全智能体 + 模式合规智能体的组合在 F1 上达到 71.1%，优于通用智能体的 60.6%

### 六大最佳实践

1. **使用独立的代码审查 harness**：代码生成与代码审查分离
2. **运行预 PR 审查**：减少开发者注意力负担
3. **提供详尽的任务级上下文**：让 AI 审查有"标准"对照
4. **提供仓库和组织标准作为上下文**：Confluence 工程标准、智能体技能、相关仓库
5. **按风险级别审查代码**：低风险（自动修复）、中风险（建议关注）、高风险（必须处理）
6. **创建新的规则和智能体技能**：Review → Judge → Capture → Reuse 循环，让代码库学习

### 评估指标

- **精确率（Precision）**：代码审查结果与已知结果的匹配程度
- **召回率（Recall）**：实际捕获的已知问题集的比例
- **F1 分数**：精确率和召回率的平衡

### 低质量 AI 代码审查系统的常见问题

- **嘈杂的评论（Noisy comments）**：低精度的表现
- **低召回（Low recall）**：遗漏真实问题
- **弱证据（Weak evidence）**：无法提供指向代码行或文件的证据
- **上下文差距（Context gap）**：无法检测标准的演变

### AI 代码审查系统的底层工作流程

1. 当开发者打开 PR 时，一个或多个 AI 智能体被触发
2. 智能体从知识库检索上下文
3. 分析变更并生成候选发现
4. 系统合成、排序和过滤发现
5. 开发者看到代码问题、解释和建议的修复
